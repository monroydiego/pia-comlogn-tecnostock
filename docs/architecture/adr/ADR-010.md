# ADR-010. Claves de negocio de texto y esquema relacional normalizado

**Estado:** Aceptada (nueva en el PIA)

## Contexto
En la Fase 3 las claves quedaron como texto (`TEC-P001`, `APT-000001`, `SUC-01`) y el esquema solo tenía 2 claves foráneas: las referencias entre aggregates (por ejemplo `Apartados.UnidadId`) eran columnas sueltas y cinco columnas guardaban varios valores (una lista separada por comas y cuatro JSON). Al revisar el esquema con respecto a las formas normales hubo que decidir si el tipo de las claves era el problema y qué corregir.

## Alternativas
1. Claves enteras `IDENTITY` para todo, con el código de negocio como columna única aparte.
2. Mantener las claves de negocio de texto y corregir la integridad y la atomicidad.
3. Dejar el esquema como estaba y justificar las referencias en la aplicación.

## Decisión
Alternativa 2.

**Las claves de texto se mantienen** porque el tipo de dato de una clave no viola ninguna forma normal; esas formas tratan la atomicidad y las dependencias respecto de la clave. Además son claves naturales y estables: `TEC-P001` y `TEC-C001` son los identificadores de los datos del curso, `SUC-01` es el código de sucursal y el folio (G-32) se imprime en el comprobante. El dominio los asigna antes de guardar (los eventos ya llevan el folio), cosa que un `IDENTITY` no permite porque solo existe después del `INSERT`. Donde no hay código humano se usa clave sustituta (`UnidadId` es `uniqueidentifier`). Los códigos se guardan como `varchar` (solo ASCII). Un folio como `APT-000001` se trata como identificador opaco y atómico.

**Integridad referencial.** Cada referencia entre aggregates lleva clave foránea en la base de datos (18 en total), sin propiedades de navegación en el dominio, de modo que ADR-002 (referencia por identidad) se conserva. Se agrega la tabla `Sucursales` (SUC-01 a SUC-05) y la FK de `Clientes`. Ninguna FK borra en cascada. Una violación de clave foránea se traduce a `NoEncontrado` (404) con un mensaje del negocio.

**Primera forma normal.** No hay columnas con varios valores:

| Antes | Ahora |
|---|---|
| `MetodosAutorizados` (lista separada por comas) | tabla `PoliticaMetodosDePago` |
| `PlazoDeDevolucion…` (JSON) | tabla `PoliticaPlazosDeDevolucion` |
| `Devoluciones.Dictamen` (JSON) | tabla `DevolucionResultadosDeRegla` |
| `Devoluciones.Decision` y `Apartados.Cancelacion` (JSON) | columnas `Decision…` y `Cancelacion…` |
| `Comprobantes.Detalle` (texto con saltos de línea) | tabla `ComprobanteLineas` |

El dominio conserva su API: `PoliticaComercial.MetodosAutorizados`, `PlazoDeDevolucionEnDiasPorCategoria` y `Devolucion.Dictamen` ahora se calculan a partir de colecciones que EF mapea a esas tablas.

**Excepciones deliberadas:**
- `Comprobantes.FolioDeOperacion` apunta a un apartado, una venta o una devolución según `Tipo`; al ser polimórfica no lleva FK.
- `LineasDeVenta.Serie`, `LineasDeVenta.PrecioUnitario` y `Apartados.PrecioAcordado` repiten datos que podrían derivarse de la unidad o del producto, pero son hechos históricos capturados al momento de la operación (G-34): la serie y el precio vigentes ese día.
- El operador (`X-Usuario`) es un Value Object que llega por encabezado, no una entidad: no hay tabla de usuarios.
- Las enumeraciones se guardan como texto sin restricción `CHECK`; las transiciones válidas las controla la máquina de estados (ADR-008).

## Consecuencias
Beneficio: la base de datos impide registros huérfanos y no depende solo de la aplicación; el esquema es consultable con SQL estándar. Costo: más tablas y uniones, y el esquema cambió con respecto a la Fase 3; como la base se crea con `EnsureCreated` (C-27), una base creada con la versión anterior debe borrarse y se vuelve a sembrar sola.

## Trazabilidad
RN-INV-002, RN-APT-003; BR-003, BR-004; US06, US17; ADR-002, ADR-009; C-35.
